# חיפוש נכס — גם תוצאות מנכס נולד (תכנון)

תאריך: 30/09/2026 · בקשת אייל · מאושר בשיחה (תשובות א/א/א/א + דרך 1)

## המטרה

חיפוש במסך הנכסים (`/v2/props`, "חיפוש נכס" מהבית) מחזיר היום תוצאות מ"המשרד שלנו", "שת"פ" ו"שלי". אייל רוצה שאותו חיפוש יחזיר גם נכסים מנכס נולד — עם כל פעולות נכס נולד, בלי לעבור מסך.

## החלטות (מהשיחה)

| # | שאלה | החלטה |
|---|------|--------|
| 1 | השהיית נכס נולד | **מבוטלת עקרונית** ("לכולם הנכסים מגיעים במיידי"). החיפוש לא מתחשב בה. הסרת המנגנון עצמו — ניקוי נפרד, לא כאן. |
| 2 | איפה מופיע | **טאב רביעי "נכס נולד"** — רק כשיש חיפוש. בלי חיפוש: קישור "לכל נכס נולד" במקומו. |
| 3 | איך מתאימים | **אותה הבנה חכמה** של חיפוש המשרד (עיר/שכונה/רחוב/חדרים/תקציב), ממוין לפי התאמה. |
| 4 | מה בכרטיס | **כרטיס נכס נולד מלא** — חיוג, וואטסאפ לבעלים, סטטוס (פגישה/פולו-אפ/לא מעוניין), הערות, "מי פנה" — נרשם בדיוק כמו במסך נכס נולד. |
| — | מבנה הקוד | **רכיב משותף** לכרטיס ולפעולות (דרך 1), לא העתקה. |

## לא בתחום

- חיפוש "שת"פ" / "משרד" / "שלי" ומסך ההתאמות בכרטיס הקונה — ללא שינוי.
- הסרת מנגנון ההשהיה (`_fetch_newborn_delays`, `NEWBORN_HIDDEN`, הגדרות בניהול) — ניקוי נפרד.
- השכרות: נכס נולד מציג מכירה בלבד (החלטה מ-31/08) — חיפוש השכרה יחזיר טאב ריק עם הסבר.

## ארכיטקטורה

### 1. שרת — `POST /api/search/newborn` (app.py)

- קלט: `{q}`. אימות: `_web_auth` (כל תפקיד).
- **פירוק משותף:** פונקציה `_parse_props_query(q)` — עוטפת את `parse_search_query` (קריאת AI) עם מטמון 10 דק' לפי הטקסט + single-flight (`_sf_lock`). גם `/api/search/properties` עובר דרכה. כך שתי הבקשות שיוצאות במקביל מהמסך עושות **קריאת AI אחת**.
- **שורות:** `fetch_newborn()` → רק בחלון `NEWBORN_WINDOW_DAYS`, בלי השהיה. כל שורה ממופה ל"שורה בפורמט המשרד" (`_nb_as_office_row`): `עיר / ישוב`, `שכונה`, `כתובת` (רחוב), `מספר בית`, `מחיר`, `חדרים`/`מ"ר`/`קומה` (מ-raw, ואם חסר — מהתיאור דרך `_famexcl_rooms/_famexcl_sqm/_famexcl_floor`), `סוג נכס` (החלק הראשון של התיאור), `סוג עסקה`=מכירה, והתיאור לזיהוי מעלית/חניה/ממ"ד.
- **ניקוד:** `search_listings_in_sheet(parsed, rows=...)` — מקבל פרמטר `rows` אופציונלי (ברירת מחדל: נכסי המשרד כמו היום), כך שאותו סולם flex ואותו `score_match` משמשים גם לנכס נולד. תקרה: 30.
- **פלט:** לכל תוצאה אותו מבנה של `/api/newborn` (key, contacted, city, address, desc, price, notes, owner, phone, wa, agent, link, date, stat, unotes, ageDays, delisted, famexcl, famexclAgent, priceDropped, priceOld) + `score`. השדות הכבדים (famexcl, פניות, הערות) — רק ל-30 הנשלחות. העוזר שבונה את השורה מחולץ מ-`api_newborn` (`_nb_row_out`) כדי ששני הראוטים ייצרו אותו פלט בדיוק.
- נרשם ביומן הפעולות כמו חיפוש נכסים (`חיפוש נכס נולד`).

### 2. רכיב משותף — `V2_NB_KIT` (effie_v2.py)

- CSS של כרטיס `.nb` + גיליון (`#sheet/#ovl` אם לא קיים בדף) + ה-JS: `nbCard`, `nbDial`, `markContact`, `waOwner`, `agOpts/agOther`, `dt15Opts/dtNextQ/dtJoin`, `stDate/stSave/stToggleNI/stSet`, `noteSheet/noteSave`, `fmtPrice`, `ST_LABEL`, והמשתנים `MYNAME/AG_OPTS/IS_COORD/OFFICE_AG/MGR/NB_WA_T`.
- **ממשק לדף המארח** (שתי פונקציות שהדף מגדיר): `nbKitRows()` — המערך שהאינדקס `i` בכרטיסים מצביע עליו; `nbKitRefresh()` — ציור מחדש אחרי פעולה.
- מסך נכס נולד: `nbKitRows = () => el('list')._src`, `nbKitRefresh = render`. **התנהגות זהה לחלוטין.**
- הרכיב מוזרק לשני הדפים (לא לכל הדפים — לא מנפח את השאר).

### 3. מסך הנכסים (`V2_PROPS_HTML`)

- צ'יפ רביעי **"נכס נולד · N"** בסגמנט (אחרי "שלי") — מופיע רק כשיש טקסט בחיפוש.
- בלי חיפוש: הצ'יפ מוסתר, ומתחת לסגמנט שורת קישור קטנה "לכל נכס נולד ←" ל-`/v2/newborn`. אם המשתמש היה בטאב נכס נולד ומחק את החיפוש — חוזרים לטאב "המשרד שלנו".
- `load(q)`: כשיש `q` — קריאה רביעית `POST /api/search/newborn` בנפרד (`step` משלה). כשל/איטיות לא מעכבים את שלושת הטאבים האחרים.
- מצב נכס נולד מצייר עם `nbCard` של הרכיב. מצב ריק מעוצב: "לא נמצאו נכסים בנכס נולד לחיפוש הזה" + הסבר על מכירה בלבד כשהחיפוש הוא השכרה.
- ה-whoami של הדף ממלא `MGR/MYNAME/AG_OPTS` כמו במסך נכס נולד (מתאמת/מנהל: בחירת סוכן בסטטוס).

## זרימת נתונים

```
הקלדה בחיפוש → load(q)
  ├─ /api/search/properties  ─┐
  ├─ /api/search/exclusives   │ (כמו היום)
  ├─ /api/my/properties       │
  └─ /api/search/newborn  ────┴─ _parse_props_query(q)  ← AI פעם אחת (מטמון+single-flight)
        → fetch_newborn → _nb_as_office_row → search_listings_in_sheet(rows=…) → top 30
        → _nb_row_out (שדות כבדים) → טאב "נכס נולד"
פעולה בכרטיס (חיוג/סטטוס/הערה) → אותם endpoints של נכס נולד → nbKitRefresh()
```

## טיפול בשגיאות

- פירוק החיפוש נכשל → טאב נכס נולד ריק עם הודעה, שאר הטאבים כרגיל.
- `/api/search/newborn` נכשל → הצ'יפ מציג "—", טוסט שקט לא נדרש.
- שורת נכס נולד פגומה → מדולגת (try פר-שורה, כמו היום).

## בדיקות

1. **שרת (python, הפונקציות האמיתיות):** מיפוי שורה (חדרים/מ"ר/קומה מהתיאור, עיר/שכונה), ניקוד ("4 חדרים בקרית ביאליק עד 2 מיליון" מדרג נכון, דירה בעיר אחרת נפסלת), תקרה 30, שדות כבדים רק ל-30, `search_listings_in_sheet` בלי `rows` = התנהגות זהה להיום, מטמון הפירוק (שתי קריאות במקביל → AI פעם אחת).
2. **רכיב משותף (node):** מסך נכס נולד מייצר **בדיוק** את אותו HTML של כרטיס לפני ואחרי ההעברה (השוואה על הקוד מ-HEAD מול החדש); פעולות קוראות ל-`nbKitRows/nbKitRefresh`.
3. **מסך הנכסים (node):** טאב מופיע רק עם חיפוש, קריאה רביעית נפרדת, כשל לא מעכב טאבים, ציור כרטיסים.
4. `ast` לשני הקבצים + בדיקת קשירת ראוטים + syntax של הסקריפטים של שני הדפים.
5. **הרצה מקומית** בדפדפן: שני הדפים נטענים בלי שגיאות קונסול.

## סיכונים

- **נגיעה במסך נכס נולד** (העברת ~250 שורות לרכיב משותף) — מכוסה בבדיקת "אותו HTML בדיוק" ובהרצה מקומית.
- **צ'אטים מקבילים** עורכים את app.py/effie_v2.py (וואטסאפ) — `git pull` לפני כל עריכה, קומיט רק של השינויים שלי.
- **דיוק ההתאמה:** בנכס נולד שכונה לא תמיד מלאה (שורות ישנות) — ניקוד השכונה החסרה כבר מטופל ב-`score_match` (+6 במקום פסילה).
